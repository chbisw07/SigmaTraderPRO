**Version:** v1.0  
**Status:** Draft for review

- multi-user authentication
- broker connectivity
- stock and basic F&O order placement

- spreads / strategy builder

### F) TradingView Webhook Integration (Frozen for M1)
Mandatory in M1.

The TradingView integration must follow a **stable, uniform webhook contract philosophy**.

### Frozen Outer Alert Contract
All TradingView strategy-based alerts must use the same alert message body:

```text
{{strategy.order.alert_message}}
```

This keeps alert setup uniform across:
- stocks
- futures
- options
- future multi-leg F&O strategies

The TradingView alert UI itself should remain minimal and transport-focused.
All strategy semantics must be generated by the Pine strategy payload.

### Frozen Inner Payload Standard
The actual structured parameters are emitted by the strategy itself using a **versioned SigmaTraderPRO JSON schema family**.

Common mandatory fields:
- `v` -> schema version
- `route_token` -> opaque secure routing token
- `strategy_id`
- `action`
- `asset_class`
- `product`
- `order_type`
- `ts`

Asset-specific fields:
- stocks -> symbol
- options -> underlying, expiry, strike, option_type
- future multi-leg -> legs[]

Example stock payload:
```json
{
  "v": 1,
  "route_token": "9f3ab2...",
  "strategy_id": "st_supertrend_v1",
  "action": "BUY",
  "asset_class": "EQUITY",
  "symbol": "INFY",
  "product": "INTRADAY",
  "order_type": "MARKET",
  "qty": 10,
  "ts": "2026-04-08T09:20:00Z"
}
```

### Secure Routing & User Resolution
The earlier digest idea is refined into a stronger production-grade design.

Each deployed strategy/user combination receives a **secure opaque routing token**.

SigmaTraderPRO must resolve from this token:
- user identity
- strategy deployment
- broker preferences
- permissions
- default execution profile

This token must be:
- unique
- unguessable
- securely stored
- rotatable

### Validation Requirements
Webhook ingestion must validate:
- route token validity
- payload schema version
- timestamp freshness
- idempotency key or dedupe signature
- canonical schema normalization
- broker dispatch eligibility

### Product Principle
TradingView remains a **uniform transport layer**.
The strategy owns payload semantics.
SigmaTraderPRO owns:
- authentication
- routing
- validation
- normalization
- broker dispatch

This frozen contract must guide all future webhook-driven workflows.

## 5.1) Canonical Broker Normalization & Instrument Registry (Frozen Core Principle)

This is one of the **most critical architectural foundations** of SigmaTraderPRO.
The entire product must operate on a **canonical broker-independent notation model**, while broker-specific identifiers, symbols, and payload differences remain strictly encapsulated inside adapters and mapping registries.

This principle has direct implications for:
- database schema design
- UI instrument rendering
- order dialogs
- webhook payloads
- multi-leg F&O workflows
- risk controls
- broker reconciliation
- future plugin integrations

### A) Canonical Core Language (System Truth)
The SigmaTraderPRO core, UI, APIs, risk engine, and multi-leg strategy workflows must speak a **single normalized notation language**.

Canonical dimensions include:
- exchange
- segment
- underlying
- expiry
- strike
- option side
- lot size
- product type
- order type
- instrument type

Example canonical identity:
`NIFTY | OPTION | 2026-04-30 | 23100 | CE`

The UI must always prioritize this canonical representation.

### B) Broker Translation Layer
Each broker adapter is responsible for converting:
- canonical instrument -> broker-native symbol/token
- broker-native payload -> canonical normalized event/order model

This applies to:
- Angel One SmartAPI
- Zerodha Kite
- Fyers API

Broker-specific formats must **never leak upward into the core product layers**.

### C) Instrument Registry (Rosetta Mapping Layer)
A durable local registry must map one canonical instrument identity to all supported broker representations.

Recommended table: `instrument_registry`

Suggested fields:
- canonical_exchange
- canonical_segment
- underlying
- expiry
- strike
- option_type
- lot_size
- angel_symboltoken
- angel_tradingsymbol
- zerodha_instrument_token
- zerodha_tradingsymbol
- fyers_symbol
- metadata_json
- is_active
- last_refreshed_at

This registry is the translation truth layer for:
- symbol search
- option chain rendering
- multi-leg strategy selection
- broker switching
- webhook routing
- reconciliation

### D) Canonical Enumerations (Frozen)
#### Exchange
- NSE_EQ
- BSE_EQ
- NSE_FNO
- BSE_FNO
- MCX_FNO

#### Segment
- EQUITY
- FUTURE
- OPTION
- INDEX
- CURRENCY
- COMMODITY

#### Product
- INTRADAY
- DELIVERY
- CARRY_FORWARD

#### Order Type
- MARKET
- LIMIT
- STOP
- STOP_MARKET

#### Option Side
- CE
- PE

Adapters must translate these to broker-native enums.

### E) UI & Workflow Principle
The user-facing UI should display **clean canonical notation**, for example:
`NIFTY 30 APR 23100 CE`

It should avoid exposing raw broker symbols unless the user is in:
- system events
- broker debug surfaces
- adapter diagnostics

This keeps the terminal clean and professional.

### F) F&O Core Implication
This normalization layer is foundational for future:
- multi-leg spreads
- condors
- straddles
- strangles
- repairs and rolls
- broker portability of live strategies
- strategy templates

Without this layer, future F&O execution workflows would become brittle.

### G) Rollout Sequence
#### Phase 1
- Angel One canonical mapping first
- registry sync and validation

#### Phase 2
- Zerodha mapping integration
- dual-broker normalization validation

#### Phase 3
- Fyers integration
- advanced chain and strategy portability

This frozen principle must guide all future broker integrations.

## 7.2) Order Dialog UX Specification (Frozen for M1)

### Visual & Interaction Direction (Angel One Inspired)
The order and positions interaction model should remain **nimble, clean, and low-friction**, inspired by the light execution feel seen in Angel One.

Design principles:
- lightweight centered trade dialog / quick drawer
- compact field grouping with minimal visual noise
- fast Buy / Sell toggles always reachable
- protection fields (SL / TP / TSL) visually grouped in one clean section
- positions row quick actions for Buy, Sell, Exit, Modify, and contextual menu
- quick hover or row-action controls on watchlist / positions for rapid maneuvering
- avoid heavy card stacking and overuse of borders
- maintain clean whitespace and restrained shadows

The implementation must borrow the **interaction speed and cleanliness**, not visually clone the broker UI.

This ticket must feel broker-terminal grade while staying modern and product-owned.

The order ticket is a **core Milestone-1 surface** and must be optimized for speed, safety, and future extensibility.

### Core M1 Decisions
- **Separate order dialogs for Stocks and F&O**
- shared underlying ticket engine for validation, payload normalization, and broker dispatch
- default broker selection must use **last successfully used broker**, persisted per user and preferably per segment (Stocks vs F&O)
- execution safety controls are included in M1: **SL, TP, and TSL**

### Broker Defaulting Behavior
The broker selector should automatically prefill:
- last used stock broker when opening stock ticket
- last used F&O broker when opening F&O ticket
- allow one-click switching to another connected broker

This behavior must feel fast and invisible to the user.

### Protection Controls Strategy
M1 order dialogs must support:
- Stop Loss (SL)
- Take Profit (TP)
- Trailing Stop Loss (TSL)

#### Execution Model (Frozen)
Use a **hybrid protective execution model**:
- prefer **broker-native SL/cover/bracket/GTT style support** where broker APIs reliably support it
- fallback to **internal protective order manager** for unsupported cases and for richer TSL workflows

This ensures:
- lower latency exits when broker-native support exists
- unified UX across Zerodha, Angel One, and Fyers
- portable behavior for future multi-leg and SigmaFNO workflows

### Stock Order Dialog (M1)
Fields:
- broker (default: last used)
- symbol
- quantity
- product: CNC / MIS
- order type: Market / Limit
- limit price (when applicable)
- optional SL
- optional TP
- optional TSL
- Buy / Sell actions
- order preview / confirmation

The stock ticket must prioritize **single-screen, low-click execution**.

### F&O Order Dialog (M1)
Fields:
- broker (default: last used)
- underlying symbol
- expiry
- strike
- CE / PE
- lots / quantity
- product: MIS / NRML
- order type: Market / Limit
- premium / limit price
- optional SL
- optional TP
- optional TSL
- Buy / Sell actions
- order preview / confirmation

The F&O ticket must optimize for **rapid strike and expiry maneuvering** without making the UI heavy.

### Architectural Intent
Although the dialogs are separate, they must be built on a **shared order ticket core engine**.

Shared responsibilities:
- field validation
- broker payload normalization
- margin preview hooks
- SL/TP/TSL normalization
- submit workflow
- preview and confirmation
- error handling and retry surfaces

This shared-core + specialized-shell design is the preferred path for future Milestone-2 multi-leg evolution.

The logging design is intentionally split into **engineering-grade structured logs** and **operator-friendly CSV audit files**.

### A) Primary Structured Application Logger
The backend must use structured logging (JSON or equivalent structured text) as the **source of engineering truth**.

Each log event should capture normalized fields such as:
- timestamp
- level
- module
- category
- event_type
- correlation_id
- user_id
- broker
- symbol
- canonical instrument key
- action
- status
- message
- metadata_json

This logger supports:
- debugging
- broker adapter diagnostics
- exception tracing
- retry visibility
- webhook flow tracing
- SL / TP / TSL lifecycle visibility
- reconciliation
- future centralized log ingestion

### B) Secondary CSV Operational Audit Files
In addition to structured logs, the system must generate **daily rotating CSV files** for easy operator inspection, Excel review, and long-term archival.

#### Naming convention
- `ST_YYYYMMDD.csv`
- `ST_YYYYMMDD_02.csv`
- `ST_YYYYMMDD_03.csv`

Example:
- `ST_20260408.csv`
- `ST_20260408_02.csv`

#### Rotation policy
Rotate on both:
- **date boundary** (new execution day)
- **maximum file size threshold**

When size exceeds threshold, create the next suffixed CSV file for the same day.

### C) CSV Schema
Recommended stable columns:
- timestamp
- level
- module
- category
- event_type
- correlation_id
- user_id
- broker
- symbol
- instrument_key
- action
- status
- message
- details

These CSV files are primarily for:
- order lifecycle review
- webhook review
- broker login/session tracing
- position sync verification
- protective exit actions
- reconciliation review
- operational debugging

### D) Security & Sanitization
Sensitive secrets must **never** be written to either structured logs or CSV audit files.

Forbidden log data includes:
- API keys
- access tokens
- refresh tokens
- TOTP secrets
- passwords
- broker session secrets

All sensitive payloads must be sanitized before persistence.

### E) Product Principle
Structured logs are the engineering truth.
CSV files are the **operator audit convenience layer**.

This dual logging model is frozen as the standard observability pattern for all future milestones.

## 7.5) Broker Authentication Lifecycle, Session Validity, Dispatch Gating & Recovery Policy (Frozen for M1)

This section defines the **practical industry-standard operational resilience model** for SigmaTraderPRO, intentionally balanced for a professional personal trading terminal without unnecessary institutional overengineering.

### A) Broker Authentication Lifecycle
Broker authentication UX should follow the proven SigmaTrader model with broker-wise settings sections.

Supported rollout order:
- Angel One first
- Zerodha second
- Fyers third

For all supported brokers, the product assumes a **daily-session validity model** based on real broker behavior.

Frozen assumption:
> broker sessions are generally valid for the current trading day only and require explicit re-authentication on a new day.

The broker settings page must show per broker:
- connection status badge
- last authenticated timestamp
- valid for today / stale session state
- reconnect action
- callback / postback URLs where applicable
- last auth error
- market data availability

### B) Persistent Status Bar (Operational Nutshell)
A thin persistent status bar must remain visible in the main workspace shell and provide at-a-glance operational truth.

Recommended contents:
- Internet: Connected / Degraded / Offline
- Broker: Connected / Session stale / Reconnect required
- Webhook: Healthy / Errors
- Dispatch: Normal / Paused / Blocked
- Market: Open / Closed
- Attention items count

Design principles:
- thin and always visible
- restrained color-coded state badges
- clickable for drill-down into Events, Brokers, or Settings
- no noisy flashing unless critical

### C) Dispatch Gating (Fail Fast Before Dispatch)
Before any live order dispatch, SigmaTraderPRO must gate the request on:
- broker session validity
- internet connectivity availability
- broker API reachability
- canonical payload validity
- risk approval
- required broker metadata presence

If any gate fails:
- **do not dispatch**
- fail deliberately and visibly
- create system event
- show status bar warning
- preserve clear reason code

This is the default M1 safety posture.

### D) Transport Resilience vs Trade Recovery
A strict distinction is frozen.

#### Allowed
Bounded transport resilience:
- safe HTTP retries
- reconnect attempts
- websocket reconnect
- broker polling fallback
- timeout handling
- DNS / TCP retry logic

#### Forbidden
Speculative market-intent recovery:
- replaying missed entries later
- recreating delayed signals after failure
- blind resubmission of stale market orders
- delayed reconstruction of time-sensitive intent

Frozen principle:
> SigmaTraderPRO may retry communication, but it must never speculate on missed market intent.

### E) Recovery Boundary
If an order has **not been safely dispatched**, the system must not attempt trade recovery.

If broker truth confirms dispatch acknowledgment:
- continue syncing broker updates
- reconcile fills, cancels, rejects, and exits
- rebuild watchers after restart if required

Recovery is therefore limited to:
- known broker-acknowledged orders
- live positions
- protective exits
- postback polling fallbacks

### F) Connectivity-Aware Failure Policy
If internet is unavailable or broker endpoints are unreachable:
- block dispatch proactively
- show Offline / Dispatch Blocked in status bar
- log structured + CSV audit event
- surface visible warning in Events workspace

This fail-fast behavior is preferred over uncertain delayed execution.

This frozen operational model must guide all future live execution workflows.

## 8) API Governance & Single Application Boundary (Frozen)

SigmaTraderPRO follows a **single versioned application API boundary**.
This is the only backend API surface for Milestone-1 and is intentionally designed to remain **simple, maintainable, and enforceable**.

### A) Frozen Principle
The React web frontend is the **primary first-party client**.
However, the API contract must remain sufficiently clean and reusable so that future **trusted internal clients**—such as console tools, quick-trade utilities, scripts, or companion dashboards—can consume the exact same endpoints.

No separate API products, client-specific route families, or special external modes should be introduced in Milestone-1.

### B) Single Versioned API Family
All backend routes must live under a single versioned namespace.

Example:
- `/api/v1/auth/...`
- `/api/v1/brokers/...`
- `/api/v1/instruments/...`
- `/api/v1/orders/...`
- `/api/v1/positions/...`
- `/api/v1/events/...`
- `/api/v1/exports/...`

This namespace is the **single trusted application boundary** for:
- frontend UI
- future CLI tools
- internal utilities
- companion systems
- approved plugin workloads later

### C) Product Benefits
This frozen model ensures:
- lower auth complexity
- one validation path
- one risk enforcement path
- one normalization layer
- one audit and logging path
- easier documentation through FastAPI OpenAPI
- future CLI reuse without extra backend work

### D) Explicit Non-Goals for Milestone-1
The following are intentionally out of scope:
- separate public developer APIs
- client-specific API variants
- special CLI-only routes
- separate API-key ecosystems
- SDK packaging
- multi-tier rate-limit products

These may be evaluated only in later milestones if truly justified.

### E) Governance Rule
Whenever a new client surface is proposed, the default decision must be:
> **reuse the existing single application API boundary**

instead of introducing a new API mode.

This principle protects long-term maintainability and keeps backend logic enforceable through one path.

## 8.1) Trade Lifecycle Data Persistence & Analytical Export (Frozen Core Principle)

SigmaTraderPRO follows a deliberate **dual data philosophy**:
- rebuildable external market data remains lean and fetched on demand where possible
- **internally generated trade lifecycle data is proprietary first-party intelligence and must be durably preserved**

This data becomes one of the most valuable long-term assets of the product.

### A) What Must Be Persisted Strongly
All system-generated trade and execution lifecycle artifacts must be stored durably in PostgreSQL.

This includes:
- orders and order events
- executions / fills / partial fills
- stock and F&O position lifecycle
- holdings snapshots and changes
- multi-leg strategy definitions
- live strategy legs and leg-level states
- SL / TP / TSL movement history
- roll, repair, and adjustment history
- broker rejection and retry outcomes
- realized and unrealized P&L snapshots
- slippage and execution quality metrics
- reconciliation outcomes
- broker response summaries
- correlation ids and linkage metadata
- user annotations or trade notes (future-ready)

This data is **not replaceable later** and must be retained as system truth.

### B) PostgreSQL as Source of Truth
The primary source of truth remains PostgreSQL.

Recommended long-lived tables include:
- trade_orders
- trade_fills
- trade_positions
- trade_position_snapshots
- fno_strategy_instances
- fno_strategy_legs
- protective_exit_events
- trade_adjustments

Retention policy:
- **indefinite retention by default**

These files are essential for:
- Excel review

- long-term performance analytics

### D) Strategic Long-Term Value
This proprietary trade dataset later powers:
- AI execution analysis
- strike and expiry quality studies
- pnl attribution
- broker performance comparison
- strategy diagnostics

## 11.1) Core vs Extensions / Plugin Readiness (Frozen Product Principle)

SigmaTraderPRO is **fundamentally an execution product**.
This principle is frozen and must guide all future milestone decisions.

The long-term health of the product depends on preserving a **trusted execution nucleus** while allowing rich surrounding capabilities to evolve through loosely coupled modules, companion services, and future plugin points.

### A) What Must Remain in the Core Product
The core terminal owns everything required for **safe, professional, and trustworthy live trade execution**.

This includes:
- user authentication and session integrity
- broker connectivity and broker adapters
- instrument search and contract resolution
- stock and F&O order dialogs
- order placement, modification, cancellation
- positions, holdings, and order book
- SL / TP / TSL orchestration
- execution-adjacent strategy management for live positions
- **core F&O multi-leg execution workflows** for live options trading
- **rapid option-chain strike discovery and multi-strike selection UX**
- **strategy-leg composition for spreads, condors, straddles, strangles, and adjustment entries**
- **option-chain driven strategy construction surfaces that directly lead to live order execution**
- hard risk controls that can veto or constrain live trades
- daily and per-symbol exposure guardrails
- protective exits and adjustment workflows
- system events and operational observability
- broker truth reconciliation
- account settings, preferences, and broker profiles

The core must remain **lean, deterministic, and highly trusted**.
No optional utility should weaken execution reliability.

**Important core clarification:**
Advanced **live F&O strategy execution itself is part of the trusted execution nucleus**.
This includes multi-leg option selection, quick strike discovery from option chain, spread construction, live adjustments, and direct strategy-leg execution workflows. These are considered integral to the broker-terminal mission and must remain in the core product.

### B) Execution-Adjacent Modules (Privileged Extensions)
Some future capabilities are close enough to live money workflows that they should remain **execution-adjacent**, even if modularized.

Examples:
- advanced multi-leg strategy management
- spread execution orchestration
- roll, repair, and adjustment workflows
- trade baskets and grouped exits
- advanced live holdings controls
- visual risk management overlays tied to actual positions
- portfolio-level enforcement helpers

These may be implemented as internal modules or privileged extensions, but they must still route through the core execution and risk layers.

### C) Potential Plugin / Companion Workloads
The following capabilities should be **decoupled by design** and integrated through APIs, event streams, companion services, or future plugin slots.

Examples:
- backtesting and simulation engines
- strategy research and optimization labs
- scanners and screeners beyond execution needs
- AI trade research assistants
- Bloomberg-like market intelligence terminals
- news and sentiment analytics
- post-trade journaling and review
- portfolio diagnostics and scenario visualization
- advanced holdings analytics dashboards
- custom research terminals and external data products

These workloads may appear as pages, tabs, or embedded panels inside the SigmaTraderPRO UI, but architecturally they must remain **loosely coupled from the execution nucleus**.

### D) Plugin Readiness Design Principles
The architecture should already preserve future readiness for plugin ecosystems.

#### Extension capabilities
A future plugin or companion system should be able to:
- consume selected market and position context
- publish insights, signals, alerts, and ranked ideas
- register approved UI panels/widgets
- subscribe to selected system events
- call permissioned SigmaTraderPRO APIs
- remain optional and removable without destabilizing the core

#### Control boundaries
Plugins must **never bypass**:
- broker abstraction layer
- risk enforcement
- policy guardrails
- order normalization
- system auditability

All live trade authority must continue to flow through the SigmaTraderPRO core.

### E) Product Governance Principle
Whenever a new feature is proposed, the first architectural question must be:

> **Does this capability directly strengthen safe live execution?**

If **yes**, it belongs in the core or execution-adjacent layer.

If **no**, it should default toward plugin, companion module, or external service integration.

This principle protects SigmaTraderPRO from long-term bloat and preserves its identity as a professional broker-terminal-grade execution product.
